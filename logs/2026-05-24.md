## Deep sleep — the big one

The whole point of the ESP32 is microamp current between samples. Without deep sleep we'd sit at ~80 mA and drain the car battery in a few days. Now:

- `lib/persistence.py` stores an 8-byte blob in RTC memory: 4-byte magic `VRM2` + uint16 `low_v_count` + 2 reserved. Survives `machine.deepsleep()` (which is a hard reset on the ESP32; nothing else but RTC memory survives).
- `controller.py` replaced the `low_v_streak_start` timestamp (broken across deep sleep because `time.time()` resets) with a sample-count approach. Each MONITORING tick increments or resets the count and persists. Trigger fires when count × WAKE_INTERVAL_S ≥ LOW_V_SUSTAIN_S.
- `run()` loop: after a MONITORING tick where we just took a sample, call `machine.deepsleep(WAKE_INTERVAL_S * 1000)`. Board resets, `load_streak()` reloads the count at the top of next `run()`.
- Other states (STARTING/RUNNING/STOPPING/COOLDOWN) stay in the regular 100ms tick loop — Pi is on and we need UART comms.

Trade-off documented in the controller docstring: manual remote-start from the dashboard only works when the ESP32 is awake, which it only is briefly between deep-sleep cycles or once a trigger has fired. By design — primary mode is voltage-trigger.

## SDR phase actual start — Vomeko dongle + Win11 USB-3 host pain

### Struggle 1: rtl-sdr Windows binaries — bad link

The doc pointed at `https://github.com/osmocom/rtl-sdr/releases` for Windows binaries. **That GitHub mirror has no releases.** Real sources are:
- Official osmocom FTP: https://ftp.osmocom.org/binaries/windows/rtl-sdr/ (fresh weekly builds)
- RTL-SDR Blog fork: https://github.com/rtlsdrblog/rtl-sdr-blog/releases (signed Windows release, includes Zadig and tuned drivers for R828D)

Fixed in commit `bb93ead`.

### Struggle 2: URH wheels on Python 3.14

`pip install urh` on Python 3.14 (current default install) fails with "You need Cython to build URH's extensions!" — URH 2.10 publishes prebuilt Windows wheels only for **cp313-win_amd64** (Python 3.13 specifically). Not 3.10, not 3.11, not 3.12, not 3.14. Linux ships wheels for 3.10–3.14.

Solution: install Python 3.13 alongside 3.14 (with "Add to PATH" unchecked), then `py -3.13 -m pip install --user urh` → `py -3.13 -m urh`. Documented after first guessing 3.12 (wrong — also no Windows wheel for 3.12). Commits `e9af934` then `750880e`.

### Struggle 3: R828D tuner + USB-3-only host = unreliable

The Vomeko dongle (R828D tuner, not R820T2 as the docs assumed — these clones ship with whichever is cheaper that batch) failed dramatically on direct USB 3.x connection:
- `Unknown USB Device (Device Descriptor Request Failed)` initially
- After Zadig: descriptor reads work, but `rtlsdr_demod_read_reg failed with -9` (USB pipe stall) on register reads
- Tuner identifies as R828D, then i2c writes fail
- Async bulk transfers crash with `cb transfer status: 4` → `5` (device dropped) and `Library error -5`

What got it working:
1. **USB 2.0 hub between the dongle and the PC.** Forces USB 2.0 negotiation, isolates the dongle from the host controller. Even an unpowered cheap hub helps.
2. **Drop sample rate to 250 kSps** instead of 2 MS/s. R828D + USB-3-only-host + budget hub can't sustain 2 MS/s reliably — `rtl_test` survives sometimes, fails other times. 250 kSps is rock-solid. For our 50 kHz-wide FOB signal, 250 kSps has 2.5× margin so it's plenty.

Both changes documented in `sdr/01` and `sdr/04`. Commits `982a051`, `f0bae96`, `7323993`.

## Late-day plot twist — this FOB isn't KeeLoq at all

The thing that broke the demodulator (~80% per-bit accuracy on Start with consistent S/S and L/L pulse pairs) wasn't a demodulator bug. The whole HCS300/KeeLoq assumption was wrong. Cross-referencing the rtl_433 project source tree found `compustar_1wg3r.c` — a device decoder for the Compustar 1WG3R family (1WG3R-SH, 1WAMR-1900) that's almost certainly the same protocol family as our 1WSHR-PRO. Key revelations:

- **Modulation: OOK_PULSE_PWM** with `short_width=708 µs`, `long_width=1076 µs`, `sync_width=1448 µs`. Not the 1:2 ratio HCS uses.
- **Fixed code.** No rolling counter, no KeeLoq encryption, no device key. Every press of the Start button transmits an identical 35-bit pattern.
- Integrity is a single inversion check (`button_inverse XOR button_code == 0xFF` in the canonical 1WG3R layout).

Empirically confirmed by re-decoding our captures with the corrected pulse widths: all 10 Start presses produce the same bits. All 10 Unlock presses produce the same different bits. The "rolling code" we'd been assuming had to exist *didn't*. That's what the (S,S)+(L,L) "decoder error" pairs were — they were sync pulses (3 of them in a row per packet) which the HCS-PWM demodulator was misclassifying.

### Implications

- KeeLoq cipher infrastructure (`esp32/src/lib/keeloq.py`) — **not needed for this FOB.** Kept in tree as future-proofing for any HCS-KeeLoq variant.
- Device-key recovery (sdr/07 walkthrough) — **not needed.** No key to recover.
- Counter management (RTC-memory persistence of a hopping-code counter) — **not needed.**
- ESP32 firmware reduces to: store 4 captured bit patterns in `secrets.py`, transmit verbatim with proper pulse widths. Capture-and-replay, not synthesize-and-encrypt.

This makes the whole project substantially simpler.

## rtl_433 ground-truth verification

Installed the nightly Windows build of rtl_433 (release 25.12 doesn't have the compustar_1wg3r decoder yet — it was added post-25.12). Ran `-A` (pulse analyzer mode) on `fob-start-lg20-b1.bin`:

```
Pulse width distribution:
 [1] count: 142, width:  732 us  [728;760]    -> "0" bit HIGH
 [3] count: 144, width: 1100 us  [1100;1108]  -> "1" bit HIGH
 [2] count:  24, width: 1476 us  [1472;1480]  -> sync HIGH

Gap width distribution:
 [0] count: 142, width:  756 us  -> LOW gap after "1" bit
 [2] count: 144, width: 1136 us  -> LOW gap after "0" bit
 [1] count:  24, width: 1500 us  -> LOW gap after sync

SNR: 42 dB
```

Two important things the analyzer told us that we'd been guessing:

1. **The protocol uses symmetric PWM.** Both HIGH and LOW vary per bit, not just HIGH. "0" = HIGH(732) + LOW(1136); "1" = HIGH(1100) + LOW(756); sync = HIGH(1476) + LOW(1500). Pulse pairs sum to ~1860 µs.
2. **Burst arithmetic checks out exactly:** 142 zeros + 144 ones + 24 syncs = 310 pulses. If each packet is `[3 syncs] + [35 data bits]` and there are 8 repeats per burst plus a ~6-pulse wake-up preamble, that's `6 + 8 × (3 + 35) = 310`. Match.

rtl_433's `-R 302` (compustar_1wg3r decoder) does NOT decode our packets — it expects 1 sync + 36 bits per packet per the canonical 1WG3R spec, but our 1WSHR-PRO transmits 3 syncs + 35 bits. The 1WSHR-PRO is a structural sub-variant of 1WG3R: same RF protocol family, same pulse widths within tolerance, slightly different framing. Since we replay verbatim (don't decode), the divergence is cosmetic.

Recorded all of this in `sdr/analysis/framing.md` (public, commit `0df2936`).

## Why surf, not Chromium — the gist

Chromium reliably OOM-killed itself on the Pi Zero 2 W (512 MB total)
while loading the dashboard. Surf (suckless WebKit2GTK) handles the
same page plus Leaflet at ~60 MB RSS without OOM, so it's the new
default. Chromium is still apt-installed by `provision.sh` as a
fallback for hardware with more headroom.

Documented in `docs/10-pi-setup.md` under a new "Why surf, not
Chromium" section.

## Dashboard map view + toggle

The dashboard now ships with **two views**:

- **Gauges view** (default): the existing battery/RPM/speed/coolant/
  throttle/fuel gauges + control buttons + trip log + events feed
- **Map view**: an embedded Leaflet map, centered (by default) on
  Edmonton city center with OSM raster tiles

A floating button in the top-right corner toggles between them.
Mouse-click in a regular browser, touch-tap on the Elecrow screen —
identical behavior. The choice is persisted to `localStorage` so a
`vroom.service` restart that reloads the page doesn't bounce the
operator back to gauges if they were watching the map.

### Configuration knobs

In `pi/app/config.py`:

```python
MAP_DEFAULT_CENTER = (53.5461, -113.4938)  # Edmonton city center
MAP_DEFAULT_ZOOM = 12
MAP_TILE_URL = "https://{s}.tile.openstreetmap.org/{z}/{x}/{y}.png"
MAP_TILE_ATTRIBUTION = '&copy; <a href=...>OpenStreetMap</a> contributors'
```

Edmonton is the shipped default because it's a public landmark — change
this constant for your install. The Jinja template renders all four
into JS land via `tojson`, so anything you set in Python flows through
without template changes.

### Implementation notes

- **Lazy Leaflet init**: the map JS is only constructed the first time
  the toggle is tapped. A kiosk operator who only ever looks at gauges
  never pays the tile-fetch cost.
- **Hidden vs. unmounted**: the map container starts `display:none`,
  which means Leaflet doesn't render tiles for an invisible div. On
  show, `invalidateSize()` is called so Leaflet recomputes its
  viewport (Leaflet famously misbehaves if its container was hidden
  at construction).
- **Subresource integrity**: both the Leaflet CSS and JS `<link>` /
  `<script>` tags have `integrity="sha256-..."` hashes pinned. If
  unpkg ever serves a different file, the browser refuses to load
  it. (Update the hashes if you bump the Leaflet version.)
- **CDN, not vendored**: matches the precedent set by the slypi-side
  `/home/node/map.html` standalone map. If the Pi is offline (no LAN
  Wi-Fi), the map view shows the page chrome but no tiles. The
  gauges view doesn't need the CDN. A future improvement is vendoring
  Leaflet into `pi/app/display/static/vendor/` so the dashboard
  works fully offline — deferred until/unless that's needed.

## Late evening — scope decision: ESP32-only is v1, Pi is v2

After looking at the dashboard map view land, took a step back to ask
"why did we add the Pi in the first place?" Honest review of the
docs:

- The vault note ([[vroom Pi-based remote start for 2009 Kia]]) and
  `docs/architecture.md` are clear: the Pi was always the *telematics*
  half. The trigger function — voltage monitoring, RF replay, run
  timer — has always been ESP32-only.
- The original ask (paraphrased): "my battery never dies in my car."
  That's pure ESP32 work.
- Everything since the SNMP responder commit is technically
  telematics: MQTT broker, dashboard hardening, kiosk stack, map
  view. None of it is wasted (all tested, all works), but **none of
  it is required for the original goal**.

Decision: **v1 ships as ESP32-only. Pi/telematics is parked as v2.**

### What this changes in the repo

Docs only — no code deleted, no slypi services stopped.

- `README.md`: rewritten to lead with the ESP32-only architecture +
  rationale + "v2 — optional telematics" section pointing at the
  parked Pi work
- `docs/BOM.md`: split into "v1 — essential (~$95)" and "v2 —
  optional telematics (+~$121)"
- `docs/architecture.md`: division-of-labor table now starts with
  v1 (everything-on-ESP32), then a "v2 add-on" section restores the
  Pi-side responsibilities; power architecture has v1 (1A buck, no
  MOSFET) + v2 (5A buck, AO3401A gate)
- `braindump.md`: pre-compaction state snapshot updated with the
  scope decision so future sessions see it on entry

### What this does NOT change

- ESP32 firmware (already works without a Pi — the Pi-power MOSFET
  GPIO toggles, `shutdown_pi` UART writes, and the STOPPING-state
  shutdown coordination are inert when no Pi is wired up)
- The `pi/` directory (kept as v2 reference build, all 199 tests
  still pass)
- slypi runtime (vroom.service stays running as the parked v2
  reference; mosquitto, SNMP, dashboard, map view all keep working
  there)
- The reproduction docs 13-20 (still useful — docs 13-16 cover
  in-car install which v1 needs; docs 17 (HA), 18 (long-term-
  stability), 19 (cellular alerting), 20 (SNMP) are v2 reference
  material)

### Why "v2" lives in the repo at all

Keeping it accomplishes three things:

1. **Reversibility** — if the v1 install gets boring after a winter
   of working perfectly and the telematics half becomes interesting,
   it's a `git pull` away. No re-derivation needed.
2. **Documentation** — the Pi-side work is, in aggregate, a pretty
   clean reference for "how to wire a Pi as a vehicle dashboard." It
   has value beyond this build.
3. **Tests stay green** — CI still exercises both halves on every
   push. Drift will catch itself.

The cost is roughly $0 — the repo has the code, tests run on free
CI, and nobody is forced to install the Pi side.

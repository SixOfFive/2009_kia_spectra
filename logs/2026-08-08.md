# 2026-08-08 — connectivity diagnosis + /powerup endpoint (fw 4.10)

## "It goes unusable until I reboot it" — diagnosed

The board kept becoming unreachable, needing a reboot to recover. Investigated
with 19.5 h of telemetry + live probing. Findings:

- **Not a resource pile-up.** Heap sat flat at ~223–229 KB and CPU at ~16–20%
  the entire time — no memory leak, no compute accumulation. So it is *not*
  RAM/CPU exhaustion.
- **The IP had moved.** `192.168.15.238` → `.153` on a reconnect (new DHCP
  lease), so every request to the old IP black-holed — a big part of the
  "it's dead" symptom. Fix going forward: reach it at **`esp32-volt.local`**
  (mDNS follows the lease) or set a DHCP reservation.
- **Weak Wi-Fi + power-save = high latency / drops.** RSSI is a consistent
  **−66 to −70 dBm** in the car (was −43 on the bench). With `wifi_ps` on, pings
  ran **avg ~800 ms, max ~3 s, ~8% loss**. Disabled power-save (`/wifips?on=0`)
  → **0% loss, avg ~346 ms.** Radio-always-on costs a little current; revisit if
  the parasitic-drain budget needs it.
- **Leading theory for the hard wedge** (reachable → totally unreachable, needs
  reboot, heap fine): **LWIP TCP socket/PCB exhaustion** — dashboard refreshes,
  Cacti/SNMP polls, browser tabs, curls opening connections that linger in
  `TIME_WAIT`/`CLOSE_WAIT` until the small pool fills and the HTTP server can no
  longer accept. A reboot clears it. The 4.9 **task watchdog does NOT catch this**
  (no task is hung). Secondary: Wi-Fi driver wedged in a failed reconnect.
- **Monitoring** launched (scratchpad `board-monitor.sh`): polls `esp32-volt.local`
  each minute, logs heap/uptime/rssi/reachability, alerts on 3 consecutive
  unreachable (the wedge) so we can catch it in the act. Baseline (PS off) clean.

Candidate follow-ups once the wedge is caught: a **Wi-Fi health watchdog that
auto-reboots on a prolonged disconnect** (so it self-recovers, no manual reboot),
tighter HTTP connection cleanup, and a socket-count metric in `/json`.

## fw 4.10 — `/powerup` endpoint

Added `POST /powerup`: one-shot, parameterless (fireable automatically like
`/reboot`). Sets **WiFi power-save OFF** and **CPU 240 MHz**, both persisted to
NVS. Returns `{"ok":true,"cpu_mhz":240,"wifi_ps":false}`. Also a **"power-up"**
link in the dashboard footer next to `reboot`. Verified: knocked the board to
CPU 80 / PS on, fired `/powerup`, both flipped to 240 / off and persisted.

## DHCP reservation + CPU back to 80

Pinned the board to **192.168.15.94** via a DHCP reservation (MAC 44:1B:F6:81:F2:50
→ .94 in dhcpd.conf on the .2 server) — IP churn solved. User pulled CPU back to
**80 MHz** (load was never the issue; PS-off is the actual link fix). Steady
config: **80 MHz + PS off + fixed .94**. A 2 h health-monitor soak showed no
wedge, heap flat, only single-cycle self-recovering blips.

## fw 4.11 — temp-compensated drain, since-last-start, rolling /logs

- **Temperature-compensated drain fit.** `computeDrain()` is now a two-variable
  least squares (V ~ time + temp). Chip temp explains ~55% of the parked voltage
  wobble (measured +5.1 mV/degC, r=0.74 over 26 h), so the plain V-vs-time slope
  was noisy. The time term is now the true depletion rate with the diurnal swing
  removed; falls back to the plain fit if temp is flat. Reports the coefficient
  (`drain_mvpc`) in the tile + `/json`. **Immediate payoff:** raw fit read ~−24
  mV/h, temp-compensated reads **~−4 mV/h** — most of the apparent "drain" was
  thermal, not depletion. Trigger stays on raw voltage (cold dip = valid reason
  to start).
- **Since last start** tile (elapsed, e.g. "3h 24m ago") next to the timestamp.
- **Rolling event log**: fixed 120-line RAM ring (can't grow → can't fill RAM or
  flash). Captures boot / WiFi up-lost-rejoin / engine starts / CPU+PS+powerup
  changes / reboots. Viewer at **`/logs`** (separate page, auto-refresh at a
  settable interval, persisted per-browser) + raw **`/logtext`**; `logs` link in
  the footer.

## fw 4.12 / 4.13 — richer event log

- **4.12**: log lines carry full `YYYY-MM-DD HH:MM:SS` (was time-only).

  - **Low-heap** warning (latched, fires once per crossing below 40 KB).
  - Set `TZ` early so even the boot line is local time (was UTC pre-NTP).
  - Deliberately **not** logging SNMP polls / per-HTTP requests (would flood).
- **4.14**: debounce DISCONNECT logging. Out of range the driver retries every
  few seconds, each firing a disconnect event -- as first written that would dump
  ~50+ identical `no-AP-found` lines and blow the 120-line ring. Now it logs the
  first, suppresses identical repeats for 2 min, and reports the count
  (`[+N more suppressed]`). Keeps the log usable during a drive-away / outage.

## fw 4.17 -- event log persisted to flash

The RAM-only 1000-line PSRAM log ring was wiped on every reboot -- useless for
"what happened right before it rebooted". Now mirrored to a small **rolling
file** on LittleFS: append new lines to `/log.txt`, rotate to `/log.old` at 48 KB
(one generation kept -> ~96 KB disk cap), and on boot **replay the tail of both
back into the ring** so `/logtext` shows cross-reboot history. All flash I/O
runs from the loop core via a `g_logSeq`/`g_logPersistedSeq` cursor -- `logLine()`
only touches the RAM ring under the existing spinlock, so file writes never
happen inside the critical section or on the safety-task core. **Proven**: the
log survived multiple reboots with the pre-reboot lines intact.

## fw 4.18 -- WiFi "range profile" (802.11b-only) -- BACKFIRED, reverted

Idea: force `esp_wifi_set_protocol(11B)` + max TX to trade speed for range at the
car's ~-70 dBm spot. Against THIS AP it was a **disaster**: latency jumped to
~1.7 s / 20% loss and a watchdog-fed task starved into a **TASK-WATCHDOG reboot
loop** (every ~85-95 s; heap/CPU fine, so a stall not exhaustion). The 4.18
disconnect log showed the client fighting the AP (auth-expire, no-AP-found,
4way-handshake-timeout). Lesson: 11b sensitivity theory didn't survive contact
with the real AP.

## fw 4.19 -- revert to b/g/n + rich WiFi telemetry

## KNOWN ISSUE (found after the 4.20 commit) -- occasional TASK-WATCHDOG resets

Reading the persistent boot log after a drive: the tight 85 s reboot loop is
gone (that was the 4.18 11b misstep), but the board still takes **isolated
TASK-WATCHDOG resets** -- fw 4.19 at 16:26 & 16:38, fw 4.20 at 17:02. They
**correlate with being off home WiFi**: the 17:02 reset landed right as the board
rejoined home after a ~15 min AP-fallback block (rssi=0 in history = the user's
drive there and back -- also visible as two crank-dip -> charge humps in the
voltage graph). So a task stalls when WiFi is disrupted; the watchdog catches it
and auto-reboots (self-recovery working), which is why uptime read ~15 min not
~35 min post-flash. I had over-claimed 4.19 "killed the loop" -- accurate: the
LOOP is dead, isolated watchdog resets are not. **Deferred** (user: "leave it for
now", it self-recovers in ~30 s). Next: `esp_task_wdt` user handler to log the
culprit task name to flash before reset + harden the WiFi-loss/reconnect path so
the safety task isn't starved. See memory `project_vroom_wdt_resets`.

## fw 4.21 / 4.22 / 4.23 -- log paging, WDT breadcrumbs, CPU-route fix, drain cap

Batch, browser-validated then flashed (the 4.23 OTA finally stuck at -70 dBm):

- **4.21 server-side log pagination.** /logs was fetching the ENTIRE /logtext then
  slicing in-browser -- useless on a flaky link. New `/logpage?p=N` returns the
  total on line 1 then just that page's 25 lines (newest-first, from the ring).
  /logs fetches one page per view (~1.5 KB vs the whole log). /logtext stays the
  full raw dump behind the "raw" link.
- **4.21 WDT-culprit breadcrumbs.** Both watched tasks (loop + safety) stamp a
  "what am I doing" marker into `RTC_NOINIT` memory (survives the reset). Next
  boot, if reset==TASK_WDT, the persistent log gets
  `^ WDT stall: loop was 'X', safety was 'Y'`. Diagnostic-only; Part B (the fix)
  still deferred.
- **4.22 CPU-button bug (regression from the 4.20 tab split).** The CPU *tab* was
  `server.on("/cpu", handleCpuPage)` with no method -> matched GET AND POST ->
  shadowed the HTTP_POST handleCpu -> POST /cpu got page HTML -> "CPU request
  error". Fix: all page routes HTTP_GET. Audited every route -- /cpu was the only
  shadowed button. Verified live: POST /cpu?mhz=80 -> {"ok":true,...}.
- **4.22 -> 4.23 drain-spike fix (two tries).** A just-settled/post-gap fit shows
  a steep spurious slope -> graph spike + bogus ~4 h ETA. 4.22 gated on r2>=0.6 AND
  win>=1 h, but a reboot-spanning fit (win 8810 s > 56 min uptime) read -112 mV/h
  at r2 0.65 and passed, ETA still 3.9 h. 4.23 adds a physical-plausibility cap:
  |rate|>40 mV/h isn't real parked drain (reboot-spanning fit / CPU-clock voltage
  step / post-drive surface-charge settle) -> drainTrusted() false -> graph 0, ETA
  -1 ("settling"). Trigger is voltage-threshold based, so capping the projection is
  safe. Verified on 4.23: drain_mvph -91.8 but as_eta_s -1. A believable slow slope
  (<40 mV/h) still yields a real days/weeks ETA; a holding battery shows "holding".

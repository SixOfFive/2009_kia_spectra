## Deep sleep — the big one

The whole point of the ESP32 is microamp current between samples. Without deep sleep we'd sit at ~80 mA and drain the car battery in a few days. Now:

- `lib/persistence.py` stores an 8-byte blob in RTC memory: 4-byte magic `VRM2` + uint16 `low_v_count` + 2 reserved. Survives `machine.deepsleep()` (which is a hard reset on the ESP32; nothing else but RTC memory survives).
- `controller.py` replaced the `low_v_streak_start` timestamp (broken across deep sleep because `time.time()` resets) with a sample-count approach. Each MONITORING tick increments or resets the count and persists. Trigger fires when count × WAKE_INTERVAL_S ≥ LOW_V_SUSTAIN_S.
- `run()` loop: after a MONITORING tick where we just took a sample, call `machine.deepsleep(WAKE_INTERVAL_S * 1000)`. Board resets, `load_streak()` reloads the count at the top of next `run()`.
- Other states (STARTING/RUNNING/STOPPING/COOLDOWN) stay in the regular 100ms tick loop — Pi is on and we need UART comms.

Trade-off documented in the controller docstring: manual remote-start from the dashboard only works when the ESP32 is awake, which it only is briefly between deep-sleep cycles or once a trigger has fired. By design — primary mode is voltage-trigger.

## Integration tests

`esp32/tests/test_integration.py` builds a paired in-memory UART pipe, wraps one end in the ESP32-side `UartLink` and the other in the Pi-side `Esp32Link`, then drives the controller through realistic scenarios:

- MONITORING sample → STATUS message decodes correctly on Pi side
- STATUS message dispatched via `uart_listener.dispatch` flows into Pi STATE
- Pi sends `start_engine` → ESP32 dispatches → triggers RF + power-on + events → Pi sees them
- KEELOQ_TX event detail contains function + counter
- OBD message round-trips with all fields intact

Plus three explicit constant-parity tests (`TYPE_*`, `CMD_*`, `EVENT_*`) that fail loudly if `pi_link.py` and `esp32_link.py` drift on any shared constant name or value.

## Even later — simulator, MQTT subscriber, power budget, pre-flight check

Couple more rounds added (`b344acf`, plus pre-flight in this round):

- **`esp32/scripts/simulate.py`** — CPython driver that runs the controller through three scripted scenarios with mocked hardware (`low_voltage` full cycle, `manual` command dispatch, `long_idle` no-spurious-trigger). Every emitted UART message printed in human-readable form. Useful for hands-on protocol debugging without burning a board. ASCII-only after fighting Windows cp1252.

- **MQTT command subscriber** (`pi/app/comms/mqtt_subscriber.py`) — closes the home-network loop. Subscribes to `<prefix>/cmd` on the same broker the publisher uses; whitelist forwards `start_engine` / `stop_engine` / `ping` / `set_threshold` to the ESP32, drops everything else. Wired into daemon.py alongside listener + publisher. Shares `state.ESP32_LINK_LOCK` with Flask so concurrent commands don't interleave UART bytes. Now you can `mqtt.publish vroom/spectra/cmd '{"cmd":"start_engine"}'` from Home Assistant.

- **`docs/power-budget.md`** — end-to-end current-draw analysis confirming the architecture meets the "weeks parked" goal: ~9.5 mA from us + ~30 mA car parasitic = ~26 days to first trigger from a full battery. Net-restorative: each 15-min run dumps ~4.8 Ah back via alternator. LM2596 quiescent is the dominant load on our side; swap to TPS62291 if real-world parked drain comes in worse than predicted.

- **`tools/preflight.py`** — runs from your dev machine to validate config thresholds, secrets presence, module imports, and optional deps (flask required, paho-mqtt optional). Catches missing-secrets-before-flash issues in <2s. `--side esp32|pi|both`, `--strict` to exit nonzero on warnings.

- **`pi/app/state.send_to_esp32(msg)`** — thread-safe write wrapper holding `ESP32_LINK_LOCK`. Used by both Flask `/api/command` and MQTT subscriber to avoid byte interleaving on the UART.

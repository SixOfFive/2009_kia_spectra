## Bug — SNMP responder serves boot-time defaults forever

The shipped `vroom-snmp.service` runs `pi.app.snmp_responder` as a
**separate process** from `pi.app.daemon`. Both `import pi.app.state`
and read `STATE`. I assumed in yesterday's design that they'd share
this dict the way threads inside one process do. They don't — module-
level dicts are per-process in CPython, so the UART listener writes
to the daemon process's dict and the SNMP responder reads its own
untouched copy. The walk confirmed:

```
.1.3.6.1.4.1.99999.7.1.0 = INTEGER: 99           # unknown
.1.3.6.1.4.1.99999.7.2.0 = Gauge32: 0            # battery_mv
.1.3.6.1.4.1.99999.7.3.0 = INTEGER: 0            # engine_running
.1.3.6.1.4.1.99999.7.4.0 = STRING: unknown       # state_name
...all the rest of the OIDs return their defaults
```

Compare to `/api/state` from the dashboard, which on the same box
shows `v_battery: 12.6`, `esp32_state: "boot"`, etc. — the daemon
process has live(ish) state; the SNMP process doesn't see it.

The wire format is fine — snmpwalk works, BER encoding is correct,
GET/GETNEXT/walk all do the right thing. The data is the problem.

### The fix (planned for next session, not today)

Run the SNMP responder as a **thread inside the main daemon**, sibling
to `uart_listener` and `mqtt_publisher`. Same process → shared `STATE`
dict. Roughly: add `snmp_responder.start_thread()` and call it from
`daemon.main()`. Delete `vroom-snmp.service`. ~30 LoC + a docs sweep
through `docs/20-snmp-integration.md` and `docs/architecture.md`.

Holding off today because (a) it's a meaningful refactor that wants
its own commit + test pass, and (b) the wire-format testing the
responder enables is still valuable on its own. Documented the
limitation in `docs/20` so anyone reading the OID table knows what
they're getting.

### Misleading systemd dependency caught while debugging

The `vroom-snmp.service` unit had `After=vroom.service` and
`Wants=vroom.service`, which implied the two services were
state-coupled. They aren't. Dropped both lines and added a comment in
the unit file explaining why.

Side-effect during debugging: the `Wants=` line was strong enough to
pull up `vroom.service` when I enabled `vroom-snmp.service`, even
though I'd never explicitly enabled vroom.service. That's how I
noticed the port-8000 collision when I tried to start the dashboard
"for the first time" — it was already running. Now both are properly
`enabled` (not just `running`).

### Side note — UDP packet loss

Saw 1/3 timeouts on direct GET requests during testing — but GETNEXT
past end of MIB resolves 3/3 cleanly, and the responder replies to
every request the kernel hands it (verified by tcpdump-adjacent
observation: the responder thread is not crashing, requests just
aren't always arriving). This is plain UDP-over-Wi-Fi loss on
slypi's BCM43430 chip with BT also active — matches the Wi-Fi/BT
coexistence quirk documented in the slypi vault note. Real SNMP
clients (snmpwalk, LibreNMS, etc.) handle this with `-r N` retries.
Not a code issue, but worth knowing so a future "why does SNMP
sometimes lag" doesn't get chased through the responder code.

Four small follow-ups landed in commit `ed814fe`, plus runtime

### 1. Baseline: full test suite on slypi's Python 3.13

CI runs the test matrix on 3.10/3.11/3.12; slypi has 3.13 (Debian
trixie default). `192/192` passing on 3.13, no surprises. 3.13's

### 2. `uart_listener` error-suppression

Pre-fix, the per-second `[uart-listener] ERROR recv` spam (port
doesn't exist → identical errno-2 every loop iteration) was a real
problem in the journal — 86,400 identical lines per day if the ESP32
takes a few days to arrive. Fixed by adding repeated-error
suppression in `listen_forever`:

- First instance of an identical error logs immediately (so the
  operator sees the problem at boot)
- Further identical errors are suppressed for 60s
- A single "still failing" summary line lands at the end of each
  window with the count and elapsed time
- When recv() recovers, a "recv() recovered" line is logged

Implementation made `time.monotonic` and `time.sleep` injectable so
the new 5 tests in `pi/tests/test_uart_listener.py` exercise the
suppression window without wall-clock waits.

Verified on slypi: after deploy, journal shows the first ERROR at
startup, then exactly one "[60 occurrences in last 60s]" line per
minute. Down from ~3600 lines/hour to ~60.

### 3. `vroom.service` systemd hardening

Added the same defense-in-depth directives the deleted
`vroom-snmp.service` had — `PrivateTmp`, `ProtectSystem=strict`,
`ProtectHome`, `ProtectKernel*`, `ProtectControlGroups`,
`Restrict*`, `LockPersonality`, `MemoryDenyWriteExecute`,
`RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX`. Plus
`ReadWritePaths=/var/log/vroom /var/lib/vroom` (trip log + future
state) and `DeviceAllow` for `/dev/serial0` + `/dev/ttyAMA0` +
`/dev/ttyS0`.

Intentionally **not** set: `NoNewPrivileges`. The daemon shells out
to `sudo shutdown` when the ESP32 requests power-down, and
NoNewPrivileges would block sudo's setuid escalation. Inline
comment in the unit file explains the tradeoff.

Verified on slypi: `systemctl show vroom.service` confirms
`PrivateTmp=yes`, `ProtectSystem=strict`, `MemoryDenyWriteExecute=yes`,
`RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX`. Daemon still
runs cleanly — no surprise breakage from the hardening.

### 4. `enable_uart=1` + serial-console disable + dialout group

Two-step:

```
# Append enable_uart=1 to /boot/firmware/config.txt
# (backup at config.txt.bak.20260530)
# Disable serial console (raspi-config nonint do_serial_cons 1)
sudo reboot
# Then add the daemon user to dialout so it can open /dev/serial0
sudo usermod -aG dialout $DEPLOY_USER
sudo systemctl restart vroom.service
```

After reboot + group add + restart:

```
$ ls -l /dev/serial0 /dev/ttyS0
lrwxrwxrwx 1 root root        5 May 30 16:20 /dev/serial0 -> ttyS0
crw-rw---- 1 root dialout 4, 64 May 30 16:20 /dev/ttyS0

$ sudo journalctl -u vroom.service --since "60s ago" | grep -c "ERROR recv"
0
```

Zero ERROR lines from uart_listener after restart — the port opens
cleanly, recv() returns no data (because there's no ESP32 on the
other end yet), uart_listener sleeps poll_interval and loops. Same
behavior we'll have when the ESP32 is connected-but-quiet. Exactly
the "no surprises when parts arrive" state we wanted.

slypi-specific gotchas worth knowing:

- **BCM43430 BT/Wi-Fi coexistence** — `enable_uart=1` alone is safe
  (turns on the mini-UART on GPIO 14/15; the PL011 stays wired to
  BT). Avoided `dtoverlay=disable-bt` and `dtoverlay=miniuart-bt`
  precisely because those WOULD touch BT, and slypi has paired BT
  mouse + keyboard. Post-reboot verified: `bluetoothctl show`
  reports the controller `Powered: yes`, and `wlan0` came up on the
  first reboot (didn't hit the vault-documented "wlan0 missing,
  reboot again" quirk this time).
- **Serial console was routed to `serial0`** by default in
  `/boot/firmware/cmdline.txt` (`console=serial0,115200`). That
  would have raced with the daemon for the port — `raspi-config
  nonint do_serial_cons 1` removed it. Now `cmdline.txt` has just
  `console=tty1`.
- **`node` user wasn't in `dialout`** by default — the daemon's
  first attempt to open `/dev/serial0` after reboot got
  `Permission denied: '/dev/serial0'` (errno 13, not 2). Fixed by
  adding to dialout group + restarting the service so the new
  group set takes effect. NEW gotcha worth pinning in the slypi
  vault note: **systemd does NOT re-read supplementary group
  memberships on `restart` unless the unit is fully stopped first**
  — `restart` was enough here, but in general `stop` + `start` is
  the safer pattern after a `usermod -aG`.

## Late evening — mosquitto on slypi (the MQTT broker decision)

Picked "fresh mosquitto on slypi" over "reuse an existing LAN broker"
— vroom is a self-contained appliance, no reason to couple its
plumbing to another service that could be retired independently.
slypi has 250+ MB of free RAM and mosquitto's RSS is ~3 MB, so
co-locating with `vroom.service` on the same Pi Zero 2 W is fine.

### Install + config

```
sudo apt install -y --no-install-recommends mosquitto mosquitto-clients
# Got mosquitto 2.0.21 from trixie. Debian auto-enables and starts the
# service bound to 127.0.0.1:1883 only (2.x security-by-default).
```

Default `/etc/mosquitto/mosquitto.conf` keeps persistence on (DB at
`/var/lib/mosquitto/mosquitto.db`) and logs to
`/var/log/mosquitto/mosquitto.log` — both fine, left alone. The
vroom-specific override is intentionally tiny:

```
# /etc/mosquitto/conf.d/vroom.conf
listener 1883 0.0.0.0
allow_anonymous false
password_file /etc/mosquitto/passwd
```

Only the **deltas** from the base config — duplicating any base key
(persistence_location, log_dest, etc.) is a fatal config error in
mosquitto 2.x. Hit that on the first attempt; minimal config is
correct.

### Auth

One user, `vroom`, password is 128 bits from `openssl rand -hex 16`
(cryptographic, not invented). Stored in `/etc/mosquitto/passwd`
(hashed) and in `/opt/vroom/pi/app/secrets.py` (cleartext, mode 600,
gitignored) and in the slypi vault note (unredacted). No copy of the
cleartext lives in this public log.

The password file needs `root:mosquitto` ownership (not
`mosquitto:mosquitto`) — mosquitto 2.x warns on any non-root owner
and future versions will refuse to load. Got the warning on the
first attempt; fixed with `chown root:mosquitto`.

```
sudo touch /etc/mosquitto/passwd
sudo chown root:mosquitto /etc/mosquitto/passwd
sudo chmod 0640 /etc/mosquitto/passwd
sudo mosquitto_passwd -b /etc/mosquitto/passwd vroom "$MQTT_PASS"
```

No ACLs for v1 — authenticated users can publish or subscribe
anywhere. Future improvement if multiple publishers ever share this
broker: split into per-app users (`vroom-pub` / `vroom-sub` / etc.)
with topic ACLs.

connect + 2 live publishes).

### Three protocol surfaces, one source of truth

vroom now has three ways to observe state from outside the Pi:

| Surface | Endpoint | Payload | Cadence |
|---|---|---|---|
| Dashboard JSON | `http://slypi:8000/api/state` | JSON | on-demand (browser polls every 1 s) |
| SNMPv2c | `snmpwalk slypi:1161 .1.3.6.1.4.1.99999.7` | 10 OIDs | on-demand |
| MQTT | `slypi:1883` topic `vroom/spectra/state` | JSON (retained) | every 10 s, plus retained-on-connect |

All three serve the same `state.snapshot()` dict — confirmed live
during the SNMP refactor that they return matching values (`v_battery`
in JSON = `battery_mv` in SNMP = `v_battery` in MQTT, all 12.6 V /
12600 mV / `12.6`).

## Service-file patches for this box

The shipped `pi/systemd/vroom*.service` files assume `User=pi
Group=pi` (Pi OS Lite default). This box has a different deploy user,
so:

```
sed -i "s|^User=pi$|User=$DEPLOY_USER|; \
        s|^Group=pi$|Group=$DEPLOY_USER|" \
    /etc/systemd/system/vroom.service \
    /etc/systemd/system/vroom-snmp.service
```

Not pushed back to the repo — the canonical install is still `pi`, and
this Pi is a one-off. If we end up with more non-`pi`-user hosts in the
fleet a `PI_USER` env var on `provision.sh` would be the right
generalization.

## Bug — SNMP responder serves boot-time defaults forever

The shipped `vroom-snmp.service` runs `pi.app.snmp_responder` as a
**separate process** from `pi.app.daemon`. Both `import pi.app.state`
and read `STATE`. I assumed in yesterday's design that they'd share
this dict the way threads inside one process do. They don't — module-
level dicts are per-process in CPython, so the UART listener writes
to the daemon process's dict and the SNMP responder reads its own
untouched copy. The walk confirmed:

```
.1.3.6.1.4.1.99999.7.1.0 = INTEGER: 99           # unknown
.1.3.6.1.4.1.99999.7.2.0 = Gauge32: 0            # battery_mv
.1.3.6.1.4.1.99999.7.3.0 = INTEGER: 0            # engine_running
.1.3.6.1.4.1.99999.7.4.0 = STRING: unknown       # state_name
...all the rest of the OIDs return their defaults
```

Compare to `/api/state` from the dashboard, which on the same box
shows `v_battery: 12.6`, `esp32_state: "boot"`, etc. — the daemon
process has live(ish) state; the SNMP process doesn't see it.

The wire format is fine — snmpwalk works, BER encoding is correct,
GET/GETNEXT/walk all do the right thing. The data is the problem.

### The fix (planned for next session, not today)

Run the SNMP responder as a **thread inside the main daemon**, sibling
to `uart_listener` and `mqtt_publisher`. Same process → shared `STATE`
dict. Roughly: add `snmp_responder.start_thread()` and call it from
`daemon.main()`. Delete `vroom-snmp.service`. ~30 LoC + a docs sweep
through `docs/20-snmp-integration.md` and `docs/architecture.md`.

Holding off today because (a) it's a meaningful refactor that wants
its own commit + test pass, and (b) the wire-format testing the
responder enables is still valuable on its own. Documented the
limitation in `docs/20` so anyone reading the OID table knows what
they're getting.

### Misleading systemd dependency caught while debugging

The `vroom-snmp.service` unit had `After=vroom.service` and
`Wants=vroom.service`, which implied the two services were
state-coupled. They aren't. Dropped both lines and added a comment in
the unit file explaining why.

Side-effect during debugging: the `Wants=` line was strong enough to
pull up `vroom.service` when I enabled `vroom-snmp.service`, even
though I'd never explicitly enabled vroom.service. That's how I
noticed the port-8000 collision when I tried to start the dashboard
"for the first time" — it was already running. Now both are properly
`enabled` (not just `running`).

## Later same day — SNMP refactor landed

Did the thread-in-daemon refactor that the "Known limitation" section
called out. Now one process serves both dashboard + SNMP from the
same in-process `STATE` dict.

Changes (commit `c3876a1`):

- `pi/app/snmp_responder.py` — added `start_thread()` that wraps
  `serve_forever` in a `daemon=True` thread named `vroom-snmp`. Kept
  `main()` for back-compat but it now logs a startup WARNING about
  the per-process state-staleness pitfall.
- `pi/app/daemon.py` — calls `snmp_responder.start_thread()` after
  the MQTT threads, gated on `config.snmp_ready()`.
- `pi/app/config.py` — added `SNMP_ENABLED` toggle + secrets import
  for `SNMP_COMMUNITY`/`SNMP_PORT`/`SNMP_BIND_HOST` with the same
  defaults as the example file. Added `snmp_ready()` helper.
- `pi/tests/test_snmp_responder.py` — new
  `test_start_thread_shares_in_process_state` test: spawns the
  thread, queries it, mutates the shared snapshot source, re-queries,
  asserts the response reflects the mutation. This is the explicit
  regression guard for the cross-process bug.
- `pi/systemd/vroom-snmp.service` — DELETED. No longer needed.
- `pi/setup/provision.sh` — no longer installs vroom-snmp.service.
- `docs/20-snmp-integration.md` — rewrote the architecture
  description, dropped the "Known limitation" callout, replaced with
  a much smaller "Standalone process mode (debugging only)" note.
- `docs/architecture.md` — Pi-side daemon layout is now a single-
  process table of four threads.

### Deploy on the bench Pi

Stop + disable + remove the old separate service:

```
sudo systemctl disable --now vroom-snmp.service
sudo rm /etc/systemd/system/vroom-snmp.service
sudo systemctl daemon-reload
```

Pull. First attempt failed — `git pull` refused because the local
`pi/systemd/vroom.service` and `pi/systemd/vroom-snmp.service` had
the User=pi → User=node patches from yesterday, and the remote had
deleted one of them entirely. Fix:

```
cd /opt/vroom
git checkout -- pi/systemd/       # discard local sed patches
git pull --ff-only                # now applies cleanly
sudo sed -i 's|^User=pi$|User=node|; s|^Group=pi$|Group=node|' \
    /etc/systemd/system/vroom.service
sudo systemctl daemon-reload
sudo systemctl restart vroom.service
```

Both ports on the same PID. Journal confirms:

### Side note — UDP packet loss

Saw 1/3 timeouts on direct GET requests during testing — but
GETNEXT past end of MIB resolves 3/3 cleanly, and the responder
replies to every request the kernel hands it (verified by tcpdump-
adjacent observation: the responder thread is not crashing, requests
just aren't always arriving). This is plain UDP-over-Wi-Fi loss on
the BCM43430 chip with BT also active — matches the
"Wi-Fi/BT coexistence" quirk documented in the vault. Real SNMP
clients (snmpwalk, LibreNMS, etc.) handle this with `-r N` retries.
Not a code issue.
